# 三阶段动态对照

此实验使用框架0.1.1的同一个原生后端，比较默认调度、固定1ms、固定20ms及Agent。依赖已经部署的`/root/euler-bench` 0.1.1和nginx、wrk、sysbench、taskset。无需更改内核或安装数据库。

## 执行

在目标openEuler root终端，其他实验结束且sched_ext为disabled时：

```bash
cd /root/oe-resource-agent
python3 experiments/run_dynamic.py --mode smoke
python3 experiments/run_dynamic.py --mode quick
```

smoke每策略一次、每阶段两个3秒窗口，主要检查进程、直方图与清理；最短驻留会影响短阶段，不能用它判断完整适应效果。

quick使用冻结的`experiments/dynamic-profile.json`：四策略各三次，固定seed在每周期内打乱顺序。每次6秒预热，随后“网页20秒→网页加后台20秒→网页20秒”，每阶段四个5秒客户端窗口。全套约14分钟，实际时长包含启动、窗口间隙、导出和停止开销。

服务和后台共享CPU0，客户端CPU1，控制器CPU2；32连接、4KiB确定性页面。实验独占框架与基准控制锁，只停止自身子进程，结束后核对默认调度恢复。

## 指标含义

- 请求吞吐：`active_rps`用实际客户端测量时长；包含窗口间隙的吞吐另以阶段wall时间计算。
- 阶段延迟：合并每个窗口的真实wrk报告桶计数，重新计算p50/p95/p99；禁止平均窗口p99。
- wrk分布包含工具自己的统计修正，直方图样本数可以不同于完成请求数，两个数都保留。
- 后台进度：只采用完整落在HTTP测量区间内的sysbench报告区间；不足覆盖或输出延迟过大时判无效。
- 策略动作：保存开始、完成的单调时钟时间；动作与请求区间重叠的窗口标记为切换窗口，并纳入主结果。
- CPU、RSS和上下文切换：1秒procfs采样；controller进程包含测试驱动，不能把它的CPU全算作Agent开销。原生后台和辅助命令的开销另有范围限制。
- 原生审计：核对ops配置、实际时间片、扣账错误计数、正常退出及最终调度状态。控制线程异常也会使整次运行无效。

## 输出与复核

每套实验生成`results/<UTC>-dynamic-<mode>-<PID>`，包含冻结参数、代码哈希、环境和二进制信息、排程、各次原始日志、采样及结构化结果。`summary.json`给出完成数量；有效性仍需结合每次结果和原始日志复核。

工作区`research/analyze_dynamic_results.py`独立检查原始日志与结果是否一致，重算阶段分布，导出交互HTML、Markdown、JSON及逐窗口CSV。它按周期计算配对变化，不把同一次运行中的短窗口视为独立重复。

## 已知边界

闭环wrk适合当前容量与竞争探索，但不能代替固定到达率的SLO评价。3ms只是冻结配置中的示例目标。Windows宿主、温度和电源模式均可影响虚拟机结果；一次宿主CPU采样不能证明没有干扰。

0.1.1在控制器绑定CPU2后采集通用环境快照，快照中的allowed_cpus=[2]和多CPU检查失败描述的是控制器掩码；启动代码已经先核对CPU0/1/2可用。负载由taskset分别绑定。下一版应在绑定前记录原始允许集合，不修改历史快照。

当前Agent使用负载行为规则，业务p99用于独立评价，尚未进入自动决策反馈。固定速率压测与可信在线SLO适配是下一阶段工作。
