# openEuler 自适应资源管控 Agent 课程设计总结报告

版本：0.2.0，面向 openEuler 24.03 LTS-SP4（Linux 6.6.0-scx 内核）。

## 1. 项目背景与总体目标

在云原生混部（Co-location）场景下，延迟敏感型在线服务（如 Nginx Web 服务）与计算密集型离线批处理任务（如 sysbench 科学计算/批处理）往往需要共享同一物理核或虚拟核以提高资源利用率。Linux 6.6 默认的 EEVDF（Earliest Eligible Virtual Deadline First，最早合规虚拟截止期优先）调度器采用基准时间片（`sched_base_slice_ns`，本系统为 2.1ms）与通用比例份额，当在线服务线程从网络 I/O 睡眠中被唤醒时，常因批处理任务占用 CPU 且缺乏微秒级强制抢占而产生较高的排队等待（Runqueue Wait）和尾延迟（p99 Latency）。

本项目基于 **openEuler 24.03 LTS-SP4（Linux `6.6.0-scx` 内核）** 实现了一套**可观测、可解释、可在线调参、可故障自愈回退的自适应资源管控 Agent（`oe-resource-agent`，版本 0.2.0）**，集成了：
1. **eBPF `sched_ext` (SCX) 自适应内核调度后端**（支持 BPF Map 在线调整时间片与短睡眠任务唤醒抢占 `SCX_KICK_PREEMPT`）；
2. **多源工作负载感知与双模式控制平面**（基于 `procfs`/`schedstats` 的行为规则路由 + 基于连续窗口 HDR 直方图的在线业务 SLO 反馈闭环）；
3. **受管 Cgroup 进程归组与 CPU 权重隔离插件**（`resource.cgroup`）；
4. **eBPF TC 网络流量统计与端口级防护 Hook 插件**（`network.ebpf_tc`）及 **Linux LSM 安全上下文审计与策略执行插件**（`security.lsm` / `security.policy.enforce`）；
5. **标准化的 JSON Schema 工具链、持久 JSON-Lines 控制会话与可执行 Skill**。

## 3. 核心模块设计与实现亮点

### 3.1 原生 `sched_ext` 自适应调度与唤醒抢占（`native/`）
- **在线无感调参**：通过 BPF Hash Map（[`oe_control`](../native/oe_adaptive.h)）在不卸载调度器的情况下动态更新 `slice_ns`（`100 ~ 20000 µs`）和 `policy_flags`，每次更新严格核对 `map_id` 与递增 `generation` 并回读验证。
- **短睡眠唤醒抢占与虚拟时间置顶信用（`OE_POLICY_WAKEUP_PREEMPT`）**：
  - **解耦短睡眠突发窗口（`is_short_wakeup`）**：采用 `max(slice_ns * 3 / 4, 750000ULL)` 判定短睡眠任务，避免在极短时间片下误杀 Nginx `epoll` 突发。
  - **唤醒 `vtime` 置顶信用（Head-of-Queue Credit）**：解决后台 `sysbench` 仅在 `stopping` 扣账导致的唤醒排队倒置问题，赋予短睡眠唤醒任务 `vtime = vtime_now - slice` 置顶信用，配合 `SCX_KICK_PREEMPT`（每 CPU **`50µs` 限频保护**）与即时忙态标记（`busy_runs >= 1`），实现微秒级抢占响应。
- **心跳租约与失联自愈**：用户态守护进程监控 `heartbeat_ns`，一旦 Python Agent 异常退出或超时未续租，自动卸载 SCX 恢复内核默认调度（`kernel.default`）。

### 3.2 多维感知与双模式控制（`oeagent/`）
- **真实调度等待感知（`schedstats`）**：启用 `kernel.sched_schedstats=1`，[`WorkloadObserver`](../oeagent/observe.py) 直接读取 `/proc/<pid>/task/<tid>/schedstat` 计算 `run_wait_fraction`（运行队列排队等待占比）与上下文切换速率。
- **行为规则模式（`nginx-cpu` / `nginx-multi-auto`）**：当同时存在高频自愿切换/高调度等待的 `latency` 任务与高 CPU 占用的 `batch` 任务时，经连续窗口确认切入 `1ms` SCX；当批处理退出只剩单服务或纯后台时，自动回退 `kernel.default`，消除单负载场景下的额外上下文切换开销。
- **阶段二连续窗口 SLO 反馈模式（`nginx-slo` / `nginx-wakeup-slo`）**：
  - 配合定制版 `wrk2`（`--windowed`），在不重启客户端连接的情况下流式输出校准后的 HDR 延迟分布（`wrk2.hdr.window`）。
  - 实现 [`align_background_intervals`](../oeagent/business.py) 边界裁剪对齐算法，消除窗口跨越 1 秒 `sysbench` 报告边界导致的覆盖率损失。
  - [`SloGuard`](../oeagent/feedback.py) 支持**多窗口基线稳定性确认（`baseline_confirmations`）与中位数聚合**、**排队积压追赶过滤（`baseline_backlog_draining`）**，以及探测后对前台完成率、吞吐比例（≥90%）、后台 EPS 比例（≥90%）的硬约束校验与不达标自动回退冷却。

### 3.3 多维插件自动协同（`AutoPluginCoordinator`）与 SCX/Cgroup 分工机制（`oeagent/plugins.py`）
- **SCX 与 Cgroup 的“宏微双层协同分工”**：
  - 在 Linux 内核中，`cgroup v1 cpu.shares` 作用于默认 EEVDF 公平调度器，而在 `sched_ext` 激活期间任务由 BPF 调度器直接接管。本项目通过 [`AutoPluginCoordinator`](../oeagent/plugins.py) 构建了**双层互补防线**：
    1. **第一层（宏观份额兜底 — 默认调度期/确认窗口期/回退期）**：检测到混部争抢的第一时间（此时仍处于 `kernel.default` 确认窗口期，或当系统处于不支持 SCX 的回退状态），自动创建 `auto_latency (4096)` 与 `auto_batch (1024)` 并迁入对应进程，在 EEVDF 默认公平调度下立即提供 **`4 : 1`（80% vs 20%）的宏观 CPU 份额保障**；
    2. **第二层（微观抢占加速 — SCX 激活期）**：确认完成后自动激活 `scx.slice (1ms + 唤醒抢占)`，用微秒级唤醒抢占将单次排队等待压至 `~20 µs`；此期间受管 Cgroup 完整保留组归属标识，一旦后台退出或发生回退，无缝衔接并在回退后自动解绑迁回根组。
- **`network.ebpf_tc` 插件（支持双向挂载与业务白名单防误封）**：基于 [oe_net_hook.bpf.c](../native/oe_net_hook.bpf.c) 实现内核 `sched_cls` 分类器，支持 `egress`/`ingress`/`both` 挂载与实时包速率监测；当受控端口包速超过 `drop_threshold_pps` 时自动下发 `drop_target=true`（在内核网络栈 qdisc/cls_bpf 分类器层提前丢弃异常报文 `TC_ACT_SHOT`，避免进入传输层与用户态），流量平息后自动恢复；同时内置 **`PROTECTED_PORTS` 业务端口白名单（`80/443/18080/18086/18091`）**，拒绝阻断核心业务端口。
- **`security.lsm` 插件与策略执行（`security.policy.enforce`）**：自动发现内核活跃 LSM 模块栈（`lockdown, capability, yama, apparmor, bpf`），审计目标进程安全标签、Capability 掩码与 `NoNewPrivs`；同时实现安全策略执行工具 `security.policy.enforce`（兼容别名 `security.lsm.enforce`）。**系统严格区分两类任务**：
  1. **合法混部任务（Co-located Batch Workloads）**：如 `sysbench` 科学计算，保留在 `CPU0` 同核混部，依托 SCX 微秒级唤醒抢占与 Cgroup 份额实现算力隔离与高利用率；
  2. **非授权异常竞争进程（Unauthorized / Rogue Tasks）**：在 openEuler 环境中，系统进程与用户进程普遍处于 `unconfined_t` 上下文。Agent 通过工作负载配置声明（**Profile Workload Whitelist**）判定进程合法性。任何未在 Profile 白名单中申报、却在受管核心上突发高 CPU 消耗或监听异常端口的非授权进程，安全策略对其执行强制隔离约束——核验 procfs 进程状态后，将其 `nice` 强制降至最低优先级（`nice=19`）并驱逐至隔离核心（`CPU3`），杜绝非授权算力侵蚀。

### 4.2 Hyper-V 阶段一：极限容量定档（57,600 RPS）与排队雪崩现象分析
在阶段一（唤醒抢占优化前），我们先通过 Survey 测得单核 Nginx 混部极限吞吐容量约为 `64,000 RPS`，并选取 90% 极限容量点（**`57,600 RPS`**）进行了初步压力探索（详见 [baseline-measurement.md](baseline-measurement.md)）：

| 策略条件 | 场景 | 计划速率 (RPS) | 实测吞吐 (RPS) | 尾延迟 p99 (ms) | 状态转移与行为观测 |
|---|---|---|---|---|---|
| `default` | Mixed 稳态 | 57,600 | 57,604.1 | 10.807 ms | 保持默认调度 |
| `default` | Dynamic 三阶段 | 57,600 | 57,577.7 | 580.607 ms | 混合阶段发生排队积压（`completion_out_of_range`） |
| `fixed-1000` (无抢占) | Mixed 稳态 | 57,600 | 55,116.0 | 10477.567 ms | 无抢占 1ms 高频切换损耗导致吞吐差 4.3%，引发 `wrk2` 恒定速率排队雪崩 |
| `fixed-1000` (无抢占) | Dynamic 三阶段 | 57,600 | 57,599.7 | 4.839 ms | 短暂混部未达到雪崩拐点 |
| **`adaptive` (Agent)** | **Mixed 稳态** | **57,600** | **57,600.2** | **3.309 ms (-69.4%)** | **自动检测争用并切入 `1000 µs` SCX，无积压** |
| **`adaptive` (Agent)** | **Dynamic 三阶段** | **57,600** | **57,600.2** | **3.169 ms (-99.5%)** | **后台加入切入 `1000 µs`，后台退出自动切回 `kernel.default`** |

> **关键分析（为什么阶段一用 `57,600 RPS` 会出现 `10,477 ms` 异常，而正式对照采用 `25,600 RPS` + 唤醒抢占？）**：
> 1. **极限容量下的排队雪崩（Queueing Instability）**：`57,600 RPS` 已逼近 CPU0 单核混部容量极限（90% 利用率）。在**未启用唤醒抢占**的 `fixed-1000` 模式下，虽然时间片缩短到 1ms，但每次切换产生额外内核调度开销，导致实际最大可服务速率降至 `55,116 RPS`（低于发包速率 `57,600 RPS` 约 4.3%）。由于 `wrk2` 按恒定速率记账，每秒未完成的 ~2,480 个请求在队列中线性堆积，10 秒后排队延迟必然突破 `10,000 ms`（`10,477.567 ms`）。
> 2. **工作点定标与唤醒抢占引入**：这一现象直接证明了**“仅靠缩短时间片而不做唤醒抢占，不仅无法消除半片等待，还会因高频切换损耗降低极限容量”**。因此，在阶段二与正式消融矩阵（4.3–4.6 节）中，我们一方面在 BPF 调度器中引入了**短睡眠唤醒抢占与 `vtime` 置顶信用**，另一方面将标准基准速率定在 **`25,600 RPS`（约 40%~50% 常态生产负载水位）**，并在 **4.5 节补充了 `12,800 / 25,600 / 38,400 RPS` 三档速率梯度实验**，从而干净地剥离排队雪崩与调度器微观唤醒延迟。

#### 4.5.1 纯网页请求速率梯度（12,800 / 25,600 / 38,400 RPS）

> **关键理论与数据辨析（EEVDF 内核机制与变量解耦分析）**：
> 1. **Linux 6.6 EEVDF 调度内核机制辨析**：
>    - openEuler 24.03 LTS-SP4 采用 Linux 6.6 内核，已正式采用 **EEVDF（Earliest Eligible Virtual Deadline First）** 调度算法替代了传统 CFS，移除了旧有的 `sysctl_sched_latency`，核心基准参数由 `sched_base_slice_ns` 控制（本系统实测默认值为 `2,100,000 ns`，即 2.1ms）。
>    - 在 EEVDF 框架下，每个调度实体的虚拟截止期定义为 $d_i = V + \frac{q_i}{w_i}$（其中 $V$ 为虚拟运行时间基准，$q_i$ 为基准时间片，$w_i$ 为基于 Cgroup shares 或 nice 映射的权重）。实体仅在合规条件（$v_i \le V$，即 $lag_i = V - v_i \ge 0$）满足时才被允许调度，并优先挑选合法且 $d_i$ 最早的任务执行。
>    - **权重决定的是宏观带宽分配与虚拟截止期递进步长，而非即时唤醒抢占能力**：当批处理任务刚获得 CPU 并开始消耗其 2.1ms 的基准片时，前台 Nginx 突发唤醒虽然具有较小的时间片分配步长，但在 EEVDF 策略下仍需等待当前任务合规边界或切片用尽，无法在微秒级时间内无条件剥夺正在运行的任务。
> 2. **为什么开启 Cgroup 权重后平均排队等待下降了 34.0%，但 p99 尾延迟未见改善？**
>    - **平均等待时间（`avg_wait_us`）从 1556.0µs 降至 1026.7µs**：Nginx 获得 `cpu.shares=4096`（权重为 sysbench 的 4 倍），其虚拟截止期递增步长缩短为后台任务的 1/4。一旦进入合规窗口，Nginx 会以更高频次切入运行，因此每个调度周期的等待时间均值显著压缩（-34.0%）；
>    - **尾延迟 p99 仍维持在 3.846ms 甚至略有增加**：第一，遭遇极坏情况（Nginx 唤醒恰逢 sysbench 刚开始执行 2.1ms 时间片）时仍需承受毫秒级排队；第二，在权重倾斜下，进程在单核上的交替切换频次显著增加，引发前台 Nginx 与后台 sysbench 在 L1/L2 数据缓存与指令缓存（D-Cache / I-Cache）上的剧烈争用与频繁驱逐，冷缓存恢复执行拉高了尾部请求耗时。
> 3. **变量解耦与多层协同必要性**：
>    - **变量 1（Cgroup `cpu.shares=4096:1024`）**：负责**宏观算力下限兜底（Throughput Floor）**，确保恶性竞争下前台至少占有 80% 算力；
>    - **变量 2（进程 `nice=15`）**：负责**调整 EEVDF 单任务权重**，在未配置 Cgroup 层次树时辅助降低优先级；
>    - **变量 3（`sched_ext` 可编程调度器）**：负责**微观即时抢占（Microsecond Preemption）**，通过 1ms 时间片结合 `50µs` 节流的唤醒置顶机制打破 EEVDF 的毫秒级切片限制。
>    **消融实验数据表明：仅凭 Cgroup 权重无法解决在线微服务的微秒级尾延迟尖刺，必须与 `sched_ext` 微秒级唤醒抢占深度结合，才能将单次排队等待压降至 `26.8 µs`（压降 58 倍）、p99 压降至 `2.131 ms`。**

> **测试环境、攻击模型与量化机理解析**：
> - **前台主业务**：端口 18089 运行 Nginx Web 服务（25,600 RPS，绑核 CPU0）；
> - **旁路攻击靶点**：在同核 CPU0 上运行辅助高算力 HTTP 服务（端口 18095，绑核 CPU0），其每个 HTTP 请求处理函数内包含 `for i in range(40000): x += i` 的 CPU 密集自旋计算；
> - **攻击发压机**：4 个并发客户端线程持续向 18095 端口注入高频 HTTP 连接与请求洪泛；
> - **关于“丢包数（972 包）”与“HTTP 请求数”的技术辨析**：
>   - **未开启 eBPF 熔断（`drop_target=false`）时**：客户端发出的 TCP 三次握手成功建立，4 个发压线程并发推送 HTTP 请求，靶点服务在 CPU0 上以 **约 180 req/s** 的速率持续处理请求并执行密集自旋，**耗尽 CPU0 约 76.2% 的算力**，直接导致前台 Nginx 发生严重的调度饥饿，单次排队等待激增至 `1541.4 µs`（排队占比 79.5%），p99 恶化至 `3.559 ms`；
>   - **开启 eBPF TC 自动熔断（`drop_target=true`）后**：内核 TC 分类器在网络协议栈的 **排队规则（qdisc）与报文分类（`cls_bpf`）层** 直接执行 `TC_ACT_SHOT` 提前丢弃目标端口报文。经由 `lo` 本地回环发出的报文在发送方 TCP 协议栈构建后、尚未递交至接收端套接字队列前即被丢弃。被拦截的 **972 个报文均为传输层 TCP 报文（主要为 SYN 连接建立请求及客户端退避重传报文）**。由于握手包在 TC 层被直接阻断，**未成功建立任何 TCP 连接，靶点服务接收到的应用层 HTTP 请求数为 0**，全程处于 `epoll_wait` 空闲休眠（CPU0 占用率为 0.0%）。CPU0 算力被 100% 完整留给 Nginx，单次排队等待压降至 **`0.4 µs`（排队基本归零）**，p99 恢复至无干扰基线（`1.920 ms`）。

#### 4.6.3 安全策略执行（`security.policy.enforce`）与网络边界保护验证
1. **安全策略执行与非授权进程判定准则（`security.policy.enforce` / 别名 `security.lsm.enforce`）**：
   - **非授权进程判定准则**：在 openEuler 环境中，系统服务与用户进程在默认 SELinux 策略下普遍运行在 `unconfined_t` 上下文，无法单靠 LSM 标签判断行为越界。Agent 依托 **Profile Workload Whitelist（工作负载白名单机制）** 进行判定：预设 Profile（如 `profiles/nginx-multi-auto.json`）明确申报了受管合法混部任务（`comm: sysbench`，分配至 `auto_batch` 组）；
   - **分级处置策略**：对申报在案的合法混部任务，系统保留在 `CPU0` 同核混部，通过 SCX 抢占与 Cgroup 进行良性资源协调；对未在 Profile 白名单申报、却在受控核心上抢占大量算力或监听异常端口的非授权进程（如 PID 51154），安全策略将其判定为非授权入侵实体，自动执行强制隔离约束——核验 procfs 进程上下文后，将其 `nice` 强制调降至最低优先级 `19`，并将 CPU 亲和性**强制驱逐至隔离核心 `CPU3`**（`allowed_cpus: [0] → [3]`），成功杜绝非授权算力侵蚀。
2. **受保护核心业务端口白名单（`PROTECTED_PORTS`）**：主动对业务端口（如 `80`、`18086`）下发 `drop_target=true`，系统均被底层守卫拒绝并抛出 `PROTECTED_PORT_REFUSED`（验证结果为 `True`），杜绝误操作导致主站失联。
3. **网络 Hook 双向挂载**：经内核验证 `ingress` 与 `egress` 双向流量分类器均挂载成功（验证结果为 `True`）。

### 4.7 多维内核资源协同自治闭环阶段实验（`check_multi_resource_auto.py`）
为验证 Agent 不仅能自动调节 CPU 调度策略，还能根据实时运行态势**自动协同控制 Cgroup 资源隔离、eBPF TC 网络钩子与 LSM 安全审计**，我们在 [`oeagent/plugins.py`](../oeagent/plugins.py) 中实现了 `AutoPluginCoordinator` 并将其集成至 [`AgentRuntime.run()`](../oeagent/runtime.py)，使用配置 [`profiles/nginx-multi-auto.json`](../profiles/nginx-multi-auto.json) 进行了 5 阶段全自动态势切换实验（完整证据保存在 [`state/multi-resource-auto-validation.json`](../state/multi-resource-auto-validation.json)）：

| 实验阶段与动态工况 | `sched_ext` CPU 自动决策 | `resource.cgroup` 自动决策 | `network.ebpf_tc` 自动决策 | `security.lsm` 审计与实测验证结果 |
|---|---|---|---|---|
| **阶段 1：纯前台服务 (`service_only`)**<br>仅 Nginx 运行，无后台争抢，端口流量正常 | 保持 `kernel.default` (`disabled`) | 保持未隔离 (`active=false`，避免单负载额外开销) | **自动在 `lo` 挂载观测模式** (`target_port=18095`, `drop_target=false`) | **自动审计 Nginx 进程** (`lsm_stack=[lockdown,capability,yama,apparmor,bpf]`)；端口探测 `HTTP 200 OK` (`0.484 ms`) |
| **阶段 2：注入后台算力争抢 (`mixed`)**<br>CPU0 启动 `sysbench` 与 Nginx 混部争抢 | **自动切入 `scx.slice`** (`1000µs + wakeup_preempt`) | **自动创建并迁入受管组**<br>`auto_latency=4096` vs `auto_batch=1024` | 持续监测包速 (`0.0 pps < 20.0 pps`，保持放行) | **自动审计新进程 `sysbench`**；在 SCX 运行期核实双组 `cgroup.procs` PID 归属生效 |
| **阶段 3：受控端口突发洪泛 (`port_flood`)**<br>向 `18095` 端口注入突发高频请求 (`315.3 pkt/s`) | 维持 `scx.slice` 保护前台 Nginx | 维持 `4096 : 1024` Cgroup 隔离 | **检测到 `315.3 pps >= 20.0 pps` → 自动下发 `drop_target=true` (`TC_ACT_SHOT`)** | **`18095` 端口探测被内核直接丢包阻断** (`dropped_packets` 递增)，同时前台 Nginx (`18086`) 返回 `200 OK` 零受影响 |
| **阶段 4：洪泛平息 & 争抢退出 (`recovery`)**<br>端口冲击停止 + `sysbench` 退出 + Agent 停止 | **自动卸载回退 `kernel.default`** (`disabled`) | **自动解绑释放**，将 Nginx 迁回根 Cgroup (`procs=[]`) | **冷却 2 窗后自动恢复 `drop_target=false` (`TC_ACT_OK`)**，Agent 退出时自动卸载钩子 | **`18095` 端口自动恢复连通** (`HTTP 200 OK`, `0.435 ms`)；退出后零内核残留状态，控制线程 CPU 占比仅 `0.52%` |
| **阶段 5：默认调度下 Cgroup 自动赋权实测**<br>`mode=default` 同核争抢自动隔离效果 | 固定 `kernel.default` (EEVDF) | **自动识别同核争抢并下发 `4096 : 1024` 权重** | 自动挂载观测模式 | 动态多资源闭环实测前台与后台 CPU 时间占比达 **`79.9% vs 20.1%`（`3.97 : 1`）**（独立纯 CPU 争用单测 `check_cgroup_plugin.py` 实测为 **`79.8% vs 20.2%` / `3.96 : 1`**，均高度吻合理论 `4.0 : 1`） |
