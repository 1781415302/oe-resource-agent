# openEuler 自适应资源管控 Agent 课程设计总结报告

## 1. 项目背景与总体目标

在云原生混部（Co-location）场景下，延迟敏感型在线服务（如 Nginx Web 服务）与计算密集型离线批处理任务（如 sysbench 科学计算/批处理）往往需要共享同一物理核或虚拟核以提高资源利用率。Linux 默认 CFS/EEVDF 调度器采用较长的时间片与通用公平策略，当在线服务线程从网络 I/O 睡眠中被唤醒时，常因批处理任务占用 CPU 而产生较高的排队等待（Runqueue Wait）和尾延迟（p99 Latency）。

本项目基于 **openEuler 24.03 LTS-SP4（Linux `6.6.0-scx` 内核）** 实现了一套**可观测、可解释、可在线调参、可故障自愈回退的自适应资源管控 Agent（`oe-resource-agent`）**，集成了：
1. **eBPF `sched_ext` (SCX) 自适应内核调度后端**（支持 BPF Map 在线调整时间片与短睡眠任务唤醒抢占 `SCX_KICK_PREEMPT`）；
2. **多源工作负载感知与双模式控制平面**（基于 `procfs`/`schedstats` 的行为规则路由 + 基于连续窗口 HDR 直方图的在线业务 SLO 反馈闭环）；
3. **受管 Cgroup 进程归组与 CPU 权重隔离插件**（`resource.cgroup`）；
4. **eBPF TC 网络流量统计与端口级隔离 Hook 插件**（`network.ebpf_tc`）及 **Linux LSM 安全上下文审计插件**（`security.lsm`）；
5. **标准化的 JSON Schema 工具链、持久 JSON-Lines 控制会话与可执行 Skill**。

## 3. 核心模块设计与实现亮点

### 3.1 原生 `sched_ext` 自适应调度与唤醒抢占（`native/`）
- **在线无感调参**：通过 BPF Hash Map（[`oe_control`](../native/oe_adaptive.h)）在不卸载调度器的情况下动态更新 `slice_ns`（`100 ~ 20000 µs`）和 `policy_flags`，每次更新严格核对 `map_id` 与递增 `generation` 并回读验证。
- **短睡眠唤醒抢占与虚拟时间置顶信用（`OE_POLICY_WAKEUP_PREEMPT`）**：
  - **解耦短睡眠突发窗口（`is_short_wakeup`）**：采用 `max(slice_ns * 3 / 4, 750000ULL)` 判定短睡眠任务，避免在极短时间片下误杀 Nginx `epoll` 突发。
  - **唤醒 `vtime` 置顶信用（Head-of-Queue Credit）**：解决后台 `sysbench` 仅在 `stopping` 扣账导致的唤醒排队倒置问题，赋予短睡眠唤醒任务 `vtime = vtime_now - slice` 置顶信用，配合 `SCX_KICK_PREEMPT`（每 CPU **`50µs` 限频保护**）与即时忙态标记（`busy_runs >= 1`），实现微秒级抢占响应。
- **心跳租约与失联自愈**：用户态守护进程监控 `heartbeat_ns`，一旦 Python Agent 异常退出或超时未续租，自动卸载 SCX 恢复内核默认调度（`kernel.default`）。

### 3.2 多维感知与双模式控制（`oeagent/`）
- **真实调度等待感知（`schedstats`）**：启用 `kernel.sched_schedstats=1`，[`WorkloadObserver`](../oeagent/observe.py) 直接读取 `/proc/<pid>/task/<tid>/schedstat` 计算 `run_wait_fraction`（运行队列排队等待占比）与上下文切换速率。
- **行为规则模式（`nginx-cpu` / `nginx-multi-auto`）**：当同时存在高频自愿切换/高调度等待的 `latency` 任务与高 CPU 占用的 `batch` 任务时，经连续窗口确认切入 `1ms` SCX；当批处理退出只剩单服务或纯后台时，自动回退 `kernel.default`，消除单负载场景下的额外上下文切换开销。
- **阶段二连续窗口 SLO 反馈模式（`nginx-slo` / `nginx-wakeup-slo`）**：
  - 配合定制版 `wrk2`（`--windowed`），在不重启客户端连接的情况下流式输出校准后的 HDR 延迟分布（`wrk2.hdr.window`）。
  - 实现 [`align_background_intervals`](../oeagent/business.py) 边界裁剪对齐算法，消除窗口跨越 1 秒 `sysbench` 报告边界导致的覆盖率损失。
  - [`SloGuard`](../oeagent/feedback.py) 支持**多窗口基线稳定性确认（`baseline_confirmations`）与中位数聚合**、**排队积压追赶过滤（`baseline_backlog_draining`）**，以及探测后对前台完成率、吞吐比例（≥90%）、后台 EPS 比例（≥90%）的硬约束校验与不达标自动回退冷却。

### 3.3 多维插件自动协同（`AutoPluginCoordinator`）与 SCX/Cgroup 分工机制（`oeagent/plugins.py`）
- **SCX 与 Cgroup 的“宏微双层协同分工”**：
  - 在 Linux 内核中，`cgroup v1 cpu.shares` 作用于默认 CFS 调度器，而在 `sched_ext` 激活期间任务由 BPF 调度器直接接管。本项目通过 [`AutoPluginCoordinator`](../oeagent/plugins.py) 构建了**双层互补防线**：
    1. **第一层（宏观份额兜底 — 默认调度期/确认窗口期/回退期）**：检测到混部争抢的第一时间（此时仍处于 `kernel.default` 确认窗口期，或当系统处于不支持 SCX 的回退状态），自动创建 `auto_latency (4096)` 与 `auto_batch (1024)` 并迁入对应进程，在 CFS 下立即提供 **`4 : 1`（80% vs 20%）的宏观 CPU 份额保障**；
    2. **第二层（微观抢占加速 — SCX 激活期）**：确认完成后自动激活 `scx.slice (1ms + 唤醒抢占)`，用微秒级唤醒抢占将单次排队等待压至 `~20 µs`；此期间受管 Cgroup 完整保留组归属标识，一旦后台退出或发生回退，无缝衔接并在回退后自动解绑迁回根组。
- **`network.ebpf_tc` 插件（支持双向挂载与业务白名单防误封）**：基于 [oe_net_hook.bpf.c](../native/oe_net_hook.bpf.c) 实现内核 `sched_cls` 分类器，支持 `egress`/`ingress`/`both` 挂载与实时包速率监测；当受控端口包速超过 `drop_threshold_pps` 时自动下发 `drop_target=true`（`TC_ACT_SHOT` 零拷贝丢包），冷却后自动恢复；同时内置 **`PROTECTED_PORTS` 业务端口白名单（`80/443/18080/18086/18091`）**，严禁对主业务端口误下发阻断规则。
- **`security.lsm` 插件（从“只读审计”升级为“审计 + 安全策略执行”）**：自动发现内核活跃 LSM 模块栈（`lockdown, capability, yama, apparmor, bpf`），审计目标进程 Capability 与 `NoNewPrivs`；并新增 `security.lsm.enforce` 执行动作，支持对未受限（`unconfined`）后台竞争进程自动执行 **`nice` 优先级降权（如 `nice=15/19`）与隔离核（`CPU3`）亲和性强制驱逐**。

### 4.2 Hyper-V 阶段一：极限容量定档（57,600 RPS）与排队雪崩现象分析
在阶段一（唤醒抢占优化前），我们先通过 Survey 测得单核 Nginx 混部极限吞吐容量约为 `64,000 RPS`，并选取 90% 极限容量点（**`57,600 RPS`**）进行了初步压力探索（详见 [baseline-measurement.md](baseline-measurement.md)）：

| 策略条件 | 场景 | 计划速率 (RPS) | 实测吞吐 (RPS) | 尾延迟 p99 (ms) | 状态转移与行为观测 |
|---|---|---|---|---|---|
| `default` | Mixed 稳态 | 57,600 | 57,604.1 | 10.807 ms | 保持默认调度 |
| `default` | Dynamic 三阶段 | 57,600 | 57,577.7 | 580.607 ms | 混合阶段发生排队积压（`completion_out_of_range`） |
| `fixed-1000` (无抢占) | Mixed 稳态 | 57,600 | 55,116.0 | 10477.567 ms | 无抢占 1ms 高频切换损耗导致吞吐差 4.3%，引发 `wrk2` 恒定速率排队雪崩 |
| `fixed-1000` (无抢占) | Dynamic 三阶段 | 57,600 | 57,599.7 | 4.839 ms | 短暂混部未达到雪崩拐点 |
| **`adaptive` (Agent)** | **Mixed 稳态** | **57,600** | **57,600.2** | **3.309 ms (-69.4%)** | **自动检测争用并切入 `1000 µs` SCX，无积压** |
| **`adaptive` (Agent)** | **Dynamic 三阶段** | **57,600** | **57,600.2** | **3.169 ms (-99.5%)** | **后台加入切入 `1000 µs`，后台退出自动切回 `kernel.default`** |

> **关键分析（为什么阶段一用 `57,600 RPS` 会出现 `10,477 ms` 异常，而正式对照采用 `25,600 RPS` + 唤醒抢占？）**：
> 1. **极限容量下的排队雪崩（Queueing Instability）**：`57,600 RPS` 已逼近 CPU0 单核混部容量极限（90% 利用率）。在**未启用唤醒抢占**的 `fixed-1000` 模式下，虽然时间片缩短到 1ms，但每次切换产生额外内核调度开销，导致实际最大可服务速率降至 `55,116 RPS`（低于发包速率 `57,600 RPS` 约 4.3%）。由于 `wrk2` 按恒定速率记账，每秒未完成的 ~2,480 个请求在队列中线性堆积，10 秒后排队延迟必然突破 `10,000 ms`（`10,477.567 ms`）。
> 2. **工作点定标与唤醒抢占引入**：这一现象直接证明了**“仅靠缩短时间片而不做唤醒抢占，不仅无法消除半片等待，还会因高频切换损耗降低极限容量”**。因此，在阶段二与正式消融矩阵（4.3–4.6 节）中，我们一方面在 BPF 调度器中引入了**短睡眠唤醒抢占与 `vtime` 置顶信用**，另一方面将标准基准速率定在 **`25,600 RPS`（约 40%~50% 常态生产负载水位）**，并在 **4.5 节补充了 `12,800 / 25,600 / 38,400 RPS` 三档速率梯度实验**，从而干净地剥离排队雪崩与调度器微观唤醒延迟。

### 4.6 多资源闭环（SCX + Cgroup + eBPF TC + LSM）定量 A/B 消融实验

通过严格控制变量，定量测定协同扩展模块（Cgroup 权重兜底、LSM 策略限权与 eBPF TC 端口熔断）在实际故障与极端冲击工况下的独立增益：

#### 4.6.1 算力争抢双层防线：默认调度/过渡期 Cgroup+LSM 兜底 vs 完整多资源自治
在 `CPU0` 同核混部（25.6k RPS + 2 线程 `sysbench`）下对比不同层级的保护力度：

| 控制配置与防护层级 | 前台 Nginx 单次唤醒排队等待 | 前台排队时间占比 | 前台 p99 (Mean±SD) | 核心机制与量化贡献 |
|---|---|---|---|---|
| **1. 无插件默认调度 (CFS 1024:1024)** | `1506.7 ± 5.0 µs` | 78.8% | `3.546 ± 0.027 ms` | CFS 无差别平权竞争，前台等待严重 |
| **2. 开启 Cgroup(4096:1024) + LSM(nice=15) 自动兜底** | **`1107.0 ± 29.6 µs` (-26.5%)** | **76.6%** | `3.845 ± 0.043 ms` | **第一道防线生效**：在默认调度下提供 4:1 份额保障与低优先级压制，**将单次排队等待显著压降 399.7 µs (-26.5%)** |
| **3. 完整多资源自治 (SCX 1ms+抢占 + Cgroup + LSM)** | **`15.5 ± 2.1 µs` (压降 97 倍)** | **8.4% (降低 90%)** | **`1.920 ± 0.023 ms` (-45.9%)** | **双层合力最优**：在宏观 Cgroup 隔离基础上由 SCX 执行微秒级抢占，彻底消除混部干扰 |

#### 4.6.2 异常端口突发洪泛冲击：无 eBPF 熔断 vs 开启 eBPF TC_ACT_SHOT 自动熔断
在 `CPU0` 上运行前台主业务 Nginx（25.6k RPS，端口 18089），同时向 CPU0 旁路测试端口 `18095` 注入高频并发 HTTP 洪泛冲击：

| 网络防护模式 | 内核 TC 丢包拦截数 | 前台 Nginx 单次排队等待 | 前台排队时间占比 | 前台 Nginx p99 | 业务可用性与受害程度 |
|---|---|---|---|---|---|
| **1. 未开启 eBPF 熔断 (洪泛打入用户态)** | 0 包 | `1541.4 µs` | 79.5% | `3.559 ms` | 洪泛流量强行穿透内核 TCP 栈并在 CPU0 争抢算力，前台服务严重受害 |

#### 4.6.3 安全策略升级与网络熔断边界保护验证
1. **LSM 安全策略执行（`security.lsm.enforce`）**：针对未受限竞争进程（如 PID 51154），成功执行安全隔离动作——核验 procfs 读取验证，目标进程 `nice` 被强制降至 `19`，CPU 亲和性被**强制驱逐至隔离核心 `CPU3`**（`allowed_cpus: [0] → [3]`），成功杜绝非授权算力侵蚀。
2. **受保护核心业务端口白名单（`PROTECTED_PORTS`）**：主动对业务端口（如 `80`、`18086`）下发 `drop_target=true`，系统均被底层守卫拒绝并抛出 `PROTECTED_PORT_REFUSED`（验证结果为 `True`），杜绝误操作导致主站失联。
3. **网络 Hook 双向挂载**：经内核验证 `ingress` 与 `egress` 双向流量分类器均挂载成功（验证结果为 `True`）。

### 4.7 多维内核资源协同自治闭环阶段实验（`check_multi_resource_auto.py`）
为验证 Agent 不仅能自动调节 CPU 调度策略，还能根据实时运行态势**自动协同控制 Cgroup 资源隔离、eBPF TC 网络钩子与 LSM 安全审计**，我们在 [`oeagent/plugins.py`](../oeagent/plugins.py) 中实现了 `AutoPluginCoordinator` 并将其集成至 [`AgentRuntime.run()`](../oeagent/runtime.py)，使用配置 [`profiles/nginx-multi-auto.json`](../profiles/nginx-multi-auto.json) 进行了 5 阶段全自动态势切换实验（完整证据保存在 [`state/multi-resource-auto-validation.json`](../state/multi-resource-auto-validation.json)）：

| 实验阶段与动态工况 | `sched_ext` CPU 自动决策 | `resource.cgroup` 自动决策 | `network.ebpf_tc` 自动决策 | `security.lsm` 审计与实测验证结果 |
|---|---|---|---|---|
| **阶段 1：纯前台服务 (`service_only`)**<br>仅 Nginx 运行，无后台争抢，端口流量正常 | 保持 `kernel.default` (`disabled`) | 保持未隔离 (`active=false`，避免单负载额外开销) | **自动在 `lo` 挂载观测模式** (`target_port=18095`, `drop_target=false`) | **自动审计 Nginx 进程** (`lsm_stack=[lockdown,capability,yama,apparmor,bpf]`)；端口探测 `HTTP 200 OK` (`0.484 ms`) |
| **阶段 2：注入后台算力争抢 (`mixed`)**<br>CPU0 启动 `sysbench` 与 Nginx 混部争抢 | **自动切入 `scx.slice`** (`1000µs + wakeup_preempt`) | **自动创建并迁入受管组**<br>`auto_latency=4096` vs `auto_batch=1024` | 持续监测包速 (`0.0 pps < 20.0 pps`，保持放行) | **自动审计新进程 `sysbench`**；在 SCX 运行期核实双组 `cgroup.procs` PID 归属生效 |
| **阶段 3：受控端口突发洪泛 (`port_flood`)**<br>向 `18095` 端口注入突发高频请求 (`315.3 pkt/s`) | 维持 `scx.slice` 保护前台 Nginx | 维持 `4096 : 1024` Cgroup 隔离 | **检测到 `315.3 pps >= 20.0 pps` → 自动下发 `drop_target=true` (`TC_ACT_SHOT`)** | **`18095` 端口探测被内核直接丢包阻断** (`dropped_packets` 递增)，同时前台 Nginx (`18086`) 返回 `200 OK` 零受影响 |

| **阶段 5：默认调度下 Cgroup 自动赋权实测**<br>`mode=default` 同核争抢自动隔离效果 | 固定 `kernel.default` (CFS) | **自动识别同核争抢并下发 `4096 : 1024` 权重** | 自动挂载观测模式 | 实测前台 `latency` 与后台 `batch` CPU 时间占比达 **`79.8% vs 20.2%`（`3.94 : 1`，高度吻合理论 `4.0 : 1`）** |
