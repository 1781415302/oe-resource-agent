# 场景实时演示与可选四配置验证

> 当前实时控制已改为不设性能达标线的相对加权评分，见[加权 Agent 说明](weighted-agent.md)。下文保留了阈值版和可选完整对照的历史方法，5ms/80%等性能门槛不再用于当前实时 Agent。

浏览器入口为 `http://127.0.0.1:8899/`。在 Windows 执行 `scripts/start-dashboard.ps1` 建立 SSH 隧道；虚拟机通过 `oe-live-dashboard.service` 运行后台。

## 日常演示：切换场景，查看当前数据

默认运行独立实时 Agent，不启动完整四配置对照。场景下拉框只负责创建真实负载；场景名称、预设业务分类和历史报告均不传入 Agent 决策模块。

1. 在“场景实时演示”下拉框直接选择场景，切换立即生效。
2. 查看当前内核配置、Agent 阶段、实时 HTTP 探测、调度等待和后台 EPS。每次采样最多增加 5 个小探测请求，卡片标明实际样本数；这是快速趋势，不是严格的尾延迟统计。
3. wrk2 的实际 RPS/HDR 仍需校准和完整 5 秒窗口；尚未取得窗口时显示等待，不沿用上一场景数值。调度与探测通常一两秒开始刷新。
4. Agent 先收集三个有效样本，再连续确认三次调整条件，通常在几秒后试用候选。展开可选区可以查看当前实际输入和判断理由；日志记录每次真实策略变更。
5. 可使用四个手动配置按钮接管；点击“恢复自主调度”重新启用 Agent。场景切换保留当前内核配置，等待 Agent 根据新进程和实时数据判断。

纯后台场景没有前台延迟，相关卡片显示无前台进程。切场景无需刷新，滚动曲线保留前后记录并标出场景分界；缺测位置断开，不伪造零延迟。后台吞吐在纯后台场景也继续绘制。旧窗口不会充当新场景卡片的当前数据。Cgroup、TC 网络扩展仍可独立操作；不需要展开完整对照。

## 实时 Agent 的自主判断

`oeagent/live_observe.py` 从实际 PID、启动时间、CPU 亲和性、`/proc/stat`、进程 CPU 计数、线程运行状态、调度等待、HTTP 探测、后台报告和完整 wrk2 窗口生成观测。`oeagent/live_agent.py` 只接受这些观测及独立全局目标，没有场景或历史赢家字段，也不读取历史测试文件。进程变化会作废正在进行的对比，但不会直接指定配置。

候选规则是可解释的启发式反馈控制：

- CPU 持续繁忙、服务等待占比和平均等待较高时，试用 1ms 与唤醒抢占；1ms 下延迟仍未满足目标时可试用 500μs。
- 实测没有前台业务且多个后台线程持续争用 CPU 时，试用 10ms；有前台时，只有完整窗口达标且后台计算占主导，才考虑较长时间片。
- 实测压力与服务排队降低时恢复默认；没有足够证据时保留当前配置。不会为了展示而要求四组配置各赢一次。

每次修改均回读真实内核状态。候选先预热 1.5 秒，至少观察 8 秒并取得新的完整业务窗口，再核对零错误、97%–105% 完成率、全局 p99 上限和后台吞吐保留要求。延迟候选需快速探测改善至少 5%，或等待下降至少 20% 且探测未明显恶化；吞吐候选需 EPS 提高至少 3%，或 EPS 基本保留同时非自愿切换明显减少。通过才标记“实测保留”；不通过回退，失败候选暂缓 30 秒重试。24 秒仍缺候选完整窗口也回退。

默认全局目标为完整窗口 p99 ≤5ms、后台 EPS 至少保留现场基线的 80%；可单独修改，切场景不改变它。快速探测用于提出候选，完整 HDR 用于检查业务约束，两者不会混称 p99。运行中的配置仍受探测失败、连续不同完整窗口退化、后台吞吐下降及反馈过期保护。未知外部进程会通过 CPU 压力和服务等待影响判断，但没有该进程的业务报告时不能宣称保护了它的吞吐。

独立判断可在同一场景中验证：保持纯网页场景与版本不变，在另一终端运行 `taskset -c 0 sysbench cpu --threads=4 --time=25 run`。观察实际压力上升后 Agent 提出候选，压力结束后根据数据恢复。`experiments/check_live_agent.py` 可自动完成短时验证，并保存原始输入、动作、内核回读与恢复结果；它不会用场景按钮触发策略。

## 四组候选配置

| 配置 | 时间片 | 短任务唤醒抢占 |
|---|---:|---|
| 默认 EEVDF | 内核默认 | 内核默认机制 |
| 自定义 SCX | 1ms | 开启 |
| 自定义 SCX | 500μs | 开启 |
| 自定义 SCX | 10ms | 关闭 |

这是默认调度与同一个自定义 SCX 后端的三组参数，不能表述成四种独立算法。SCX 参数间切换使用原有 Map 热更新；进出默认调度需要加载或卸载后端。SCX 接管范围由后端决定，不应描述成只修改 CPU0 的内核调度。

## 八个预置场景

| 场景 | 前台 | 后台/额外负载 | 选择目标 | 窗口 p99 目标 |
|---|---|---|---|---:|
| 纯网页服务 | Nginx 静态 4KiB，25,600 RPS | 无 | 延迟 | 3ms |
| 延迟优先混部 | 同上 | sysbench 1 线程 | 延迟并保护后台吞吐 | 3ms |
| 吞吐优先混部 | 静态页面，4,000 RPS | sysbench 4 线程 | 延迟达标后比较后台吞吐 | 8ms |
| 纯后台多线程 | 关闭 | sysbench 4 线程 | 后台吞吐 | 不适用 |
| 突发请求混部 | 静态页面，8,000 RPS 主流 | sysbench 1 线程；额外 8 路连接每秒活跃 200ms | 延迟并保护后台吞吐 | 8ms |
| 请求内 CPU 计算 | Nginx 代理 PBKDF2，300 RPS | 每请求 SHA256 PBKDF2 4,000 次迭代；sysbench 1 线程 | 延迟并保护后台吞吐 | 20ms |
| 频繁休眠唤醒 | 静态页面，8,000 RPS | 4 线程，每轮 PBKDF2 300 次迭代后休眠 2ms | 延迟并保护后台吞吐 | 8ms |
| 较大工作集计算 | 静态页面，4,000 RPS | 2 线程，各反复散列 32MiB，总工作集 64MiB | 延迟达标后比较后台吞吐 | 8ms |

这些目标仅用于下方可选完整对照，不会覆盖实时 Agent 的全局目标；不是已经测出的系统容量保证，也没有为任何场景指定获胜配置。工作集大小本身不能证明某一硬件上的缓存未命中率。突发生成器使用 CPU3；Nginx、请求计算服务和后台计算使用 CPU0；wrk2 使用 CPU1；控制服务使用 CPU2。

sysbench 的 EPS 是计算事件/s，休眠唤醒负载的 EPS 是完成周期/s，工作集负载的 EPS 是完成散列/s。不同场景的 EPS 不能直接排序。突发请求的累计完成量和错误保存在独立原始日志中，不并入 wrk2 主流的 RPS 或错误计数。

## 可选：完整对照实验与历史报告

1. 主界面切换到需要验证的场景，再展开下方“可选：完整对照实验与历史报告”。
   完整对照使用上表中的实验目标；“Agent 全局业务目标”只控制独立实时 Agent，两者分开显示。
2. 选择重复轮次和每组完整窗口数。1 轮适合功能演示，2–3 轮提供更多对照；一次窗口不是一次独立进程重启实验。
3. 点“比较当前场景四组配置”。测试会暂时关闭负载与扩展操作，防止比较期间改变条件；手动接管策略或切换场景会明确作废当前搜索。
4. 观察每组内核状态、窗口数、实际 RPS、后台 EPS、错误、约束通过与否。测试不要求四组各赢一个场景。
5. 测试结束后自动应用本次选择，显示选择理由；如果全部未通过约束，恢复默认并明确报告目标未满足。
6. 顶部“自主调度”按钮控制实时 Agent，不启动完整对照。可选完整对照运行时暂停实时 Agent；结束后可点击“恢复自主调度”。用于开发验证的 `start_tuning` API 仍支持 `automatic=true`，执行完整比较和后续反馈保护。
7. “运行全部典型场景”依次执行八个场景。每场景四配置、两轮、每组三个窗口，完整测试通常需要约二十多分钟，具体取决于校准与有效窗口等待。完成后恢复纯网页与默认调度。
8. “停止测试并恢复默认”可中止测试。部分结果不会被标记为完整最优结论。
9. 使用“导出四策略测试与原始窗口”保存本次/已保存报告。已保存报告明确显示时间和 Boot ID，不参与新的实时决策。

完整比较与其自动监测期间暂停额外短周期 HTTP 探测，卡片和延迟曲线改用 wrk2 HDR 的完整窗口。选择表只收集预热结束后、不跨策略的窗口；曲线显示最近完整窗口，因此切换过渡值不代表候选的稳定测量结果。

请求内 CPU 计算场景在手动模式使用 HDR；实时 Agent 模式提供限量的小探测，以便即时展示。

## 可选完整对照的选择和保护规则

每次配置应用后预热至少 5 秒，随后收集完整 5 秒窗口，默认每组 3 个。只有同一场景、同一工作负载版本、同一组进程与策略版本的窗口可以归入该次试运行。后台报告必须覆盖窗口至少 80%，报告交付时间差不得达到 2 秒。

每轮对窗口指标取中位数，再对重复轮次取均值。显示的标准差来自重复轮次间的差异；窗口 p99 的中位数/均值不是把全部请求合并后重新计算的总体 p99。

- 有前台时要求无请求错误、每个窗口完成率在目标的 97%–105% 内，并满足该场景 p99 目标。
- 延迟目标下，后台吞吐不得低于设置的默认基线保留比例（默认 90%），随后比较窗口 p99。
- 吞吐目标下，先通过前台约束，再比较后台 EPS。
- 默认同样通过约束时，低于 5% 的尾延迟改善或低于 3% 的 EPS 提升不触发切换。
- 完整自动验证选择后，连续三个有效窗口违反业务目标或后台 EPS 比选中时下降超过 15%，回到默认；冷却 30 秒后再比较。
- 完整自动验证监测 30 秒没有有效业务反馈时恢复默认。试运行 120 秒无法收集足够有效窗口时停止并恢复默认。这不是快切模式的逐组比较流程。

实时 Agent 和完整对照均为本机受控试运行与启发式选择，不是未知业务上的全局最优保证。默认基线与候选按时间先后测量，循环调整顺序只能降低部分顺序影响，无法消除宿主机干扰或所有时间相关性。

## Cgroup、网络和安全审计

四组调度对照期间不同时改变 Cgroup 权重，以免把分组效果误当成调度器收益。Cgroup 实验仍在默认调度下独立运行；当前 SCX 后端不实现组权重语义。

自动模式的 TC 测试端口仍为 18095，CPU 场景使用的前台端口为 18091，请求计算后端为 18093。网络自动隔离采用测试端口的每采样窗口包数阈值，不能表述成通用攻击识别。LSM 部分读取标签和权限，属于审计。

## 可复核数据与测试

`GET /api/tuning/export` 返回各轮参数、内核快照、场景与进程身份、原始 wrk2 记录、后台时间区间、摘要及选择理由。完整套件保存到 `state/demo-suite-latest.json`，进行中状态单独保存，单场景报告保存在 `state/demo-tuning-runs/`。

在虚拟机运行以下命令，可通过同一个网页 API 执行全套场景，并独立重算原始请求完成速率、后台 EPS 对齐、来源摘要和内核配置：

```bash
cd /root/oe-resource-agent
taskset -c 2 python3 -u experiments/check_demo_tuning.py --repeats 2 --windows 3
```

只验证新增四类场景时可指定：

```bash
taskset -c 2 python3 -u experiments/check_demo_tuning.py --repeats 1 --windows 2 --scenarios burst compute wakeup cache
```

测试脚本会操作当前演示负载，使用前应先结束现场演示。功能验证通过不等同于每个场景的业务目标都通过；目标未满足的配置会原样保留失败原因。

## 2026-10-26 独立实时 Agent 验证

新版在本机和来宾系统均通过 145 项通用/来宾测试（未运行缺少 research 依赖的主机侧模块）。连续图的缺测断线、场景分界、纯后台吞吐和无页面刷新检查通过。

`check_live_agent.py` 实测 25.64 秒通过：整个验证保持 `service`、负载版本 0、Nginx/wrk2 PID 不变，另起一个未登记在场景中的 CPU0 sysbench 进程制造竞争。Agent 独立观察到 CPU 100%、服务等待趋势 81.1%，提出 1ms 候选。后续趋势中的等待降至 40.75%，短探测 p95 的中位数从 2.035ms 降至 0.5165ms；候选完整 5 秒窗口 p99 为 3.753ms、完成率约 99.969%、零错误，之后标记实测保留。外部压力结束后 Agent 根据低压力数据恢复默认。这里没有采集外部 sysbench 的业务吞吐作为 Agent 输入，因此不宣称保护了该外部进程的吞吐。

原始内核核验依次为 `disabled → enabled → disabled`；候选 Map 回读 `slice_ns=1000000`、`policy_flags=1`。本地证据为项目上级 `deployment-20261026/live-agent-validation.json`，包含各次原始观测、动作、完整窗口指标和 `bpftool` 输出。切场景连续性 API 复测 0.911 秒通过，保留旧曲线且新卡片不复用旧场景指标。这些是短时功能验证，不是独立重复的性能结论。

## 2026-10-26 历史完整对照验证记录

八场景、四配置、两轮、每组三个窗口已实际运行，历时 1,578 秒；192 个有效窗口全部通过来源、计时与配置核对。其中 168 个 HTTP 窗口的 p99 从原始 HDR 桶按 HDR 秩规则重算一致，24 个纯后台窗口不产生 HTTP 指标。28 次相邻 SCX 配置切换核对了 Map ID 和进程 PID 不变、generation 增加；同场景各轮的工作负载进程保持一致。

本次观察到：吞吐优先混部选择默认；纯后台多线程选择 10ms；请求内计算选择 1ms。选择取决于测量和目标，不能推广成这些场景永远固定选择某一组。两轮结果中的波动原样显示，不是统计显著性或生产环境收益保证。

纯网页与延迟混部在预置的严格目标下，四组均未通过业务约束，报告明确记录安全回退。另以明确设置的 5ms / EPS 至少保留 80% 目标，在页面完成了一轮自动寻优，实测选择 1ms；暂停本项目 wrk2 后，30 秒缺失反馈保护恢复默认，并由独立 SSH 确认 sched_ext disabled。

119 项通用和来宾相关测试通过（不含缺少 research 依赖的主机侧模块）。浏览器覆盖场景选择、目标设置、完整比较、报告查看/下载和缺失反馈回退；Cgroup 本次复测约 4.03:1，网络放行、丢包计数增加和恢复通过。
