# 当前演示 Agent：相对加权评分

当前使用 `oeagent/weighted_agent.py`。延迟与吞吐直接参与评分，不再要求 p99≤5ms 或 EPS≥80% 才能保留配置。旧版阈值实验保存在单独的数据目录，不作为新版的现场决策输入。

## 分数含义

默认权重为延迟 0.6、吞吐 0.4。基线与候选都使用完整 HDR 窗口的 p99；短探测 p95 只用于即时展示。前台存在时，Agent 等到完整业务窗口建立可比基线后才试用候选，因此曲线会先更新，策略不必立即切换。

设 `L` 为完整窗口 p99：

```text
延迟相对表现 R_L = L_基线 / L_候选
前台吞吐比 R_F = 实际RPS_候选 / 实际RPS_基线
后台吞吐比 R_B = EPS_候选 / EPS_基线
同时有两项吞吐时 R_T = sqrt(R_F × R_B)，否则采用可测的一项
综合分 S = 100 × exp((w_L × ln(R_L) + w_T × ln(R_T)) / 可测维度权重之和)
```

基线分为100，分数越高，表示按当前权重的相对表现越好。比值消除了毫秒、请求/秒、计算事件/秒等单位的影响；几何加权同时反映收益与损失。无前台时不计延迟权重，只有前台时没有后台 EPS 维度。缺少本来应有的数据时等待，不把缺测当成零。

例如基线 p99 为10ms、实际RPS不变、EPS为1000；候选 p99为7ms、EPS为700。默认权重下分数约107.4，虽然超过旧版5ms和低于旧版80%门槛，仍可因综合收益而保留。这里吞吐分同时包含实际RPS与后台EPS。

## 自主试用与保留

Agent 的输入仍只有实际进程、CPU、调度等待、请求和后台报告，不含场景名称或历史赢家。进程变化，或连续实测 CPU 繁忙度相对基线改变至少30个百分点时，旧比较作废，重新建立现场基线。

CPU竞争和线程状态只影响试用顺序：前台排队明显时优先试1ms和500μs，纯后台优先试10ms，压力较小时先考虑默认。最终是否保留由加权实测分决定，四组配置均可参与。

每次候选先经过连续确认和驻留保护，预热1.5秒，至少观察8秒；有前台时还需取得属于新配置的完整业务窗口。候选相对当前分数提高至少2%时保留，否则恢复上一配置；默认配置在分数相近的1%范围内优先，减少不必要的SCX驻留。这里的容差用于防抖，不是业务性能目标。

已测候选保留评分和观测时间。当前分数下降、且另一个已测候选领先至少5%时，会重新试用验证。90秒后刷新比较基线，防止长期使用旧负载下的分数。未试用过的配置没有实测分，不宣称已知其优劣，也不保证此刻选中全局最优。

## 保护处理

请求错误、有效数据缺失、完整业务反馈超过30秒未更新、业务进程退出及内核控制异常，仍进入保护处理。试用24秒仍缺必要反馈时恢复上一配置。被实际评分否决的候选暂缓30秒重试。

这些是控制与数据有效性保护，不是延迟或吞吐达标线。加权选择允许业务取舍，综合分更高也可能伴随某一项指标变差。

## 页面与接口

页面保留一行场景选择，下面直接显示实时数据和连续曲线。可选区域提供延迟、吞吐权重和已测配置分数。切场景不修改权重；应用权重不重启负载，也不直接指定策略。

```json
{"action":"set_agent_weights","latency":0.6,"throughput":0.4}
```

两个权重非负，且至少一项为正，内部会按可测维度归一化。旧 `set_agent_goals` 接口明确拒绝，不会暗中保留5ms/80%的规则。下方可选完整四配置对照保留了历史实验目标和报告，它运行时暂停加权 Agent，不能将旧版验收表混作当前在线评分。

## 本次实验的版本界限

第一阶段：8场景×5组配置×3轮，120次试运行，每次2个完整窗口，共240个窗口，阈值版及固定配置源码随原始数据封存。

第二阶段：8场景×默认/加权Agent×3轮，48次试运行，每次3个完整窗口。两阶段使用相同负载构造和CPU分配，统一短探测量，但窗口数不同，版本间比较只作描述性解释。新版评分的独立配对结果与源码另存，不能把第一阶段结果表述成新版实测。

对照图中的“相对默认综合分”按同轮默认重算。它和 Agent 内部的早期现场基线不是同一个参照；两者均保留原始数据，分别解释。
